# Как работает SchoolExpensesDemo (или Полный гид по школьной кассе без паники)

Привет! Если ты только начинаешь изучать **Delphi**, классический **VCL** и взрослое объектно-ориентированное программирование — добро пожаловать на борт. Заваривай чай или кофе: сейчас мы спокойно, без занудства и на понятных примерах из жизни разберём весь проект по косточкам.

Этот документ описывает **текущую** (актуальную) архитектуру приложения. Все рабочие исходники лежат в корне проекта, а в каталоге `code_explorer` живёт удобная интерактивная копия-просмотрщик с подсказками для браузера.

Если нужно запомнить главную идею всего проекта в одной фразе, держи её:

> **Пользователь взаимодействует с фреймом ➔ фрейм передаёт задачу сервису ➔ строгий сервис проверяет правила («а сумму ввели? а ученика выбрали?») и вызывает репозиторий ➔ репозиторий отправляет честный SQL в базу данных ➔ а модуль `uMainData` отдельно перечитывает данные и обновляет красивые таблички на экране.**

## 1. Что делает программа

`SchoolExpensesDemo` — это настольное Windows-приложение на Delphi/VCL для автоматизации одного из самых эмоциональных процессов в мире: **учёта денег родительского комитета класса**.

Каждый, кто хоть раз видел родительский чат в конце четверти, знает, как выглядит финансовый хаос: кто-то сдал 2000 рублей, кто-то перевёл половину, а родительский комитет уже купил рабочие тетради, мел, мыло и заказал легендарные «шторы в кабинет» на 15 400 рублей.

Наша программа берёт этот хаос в ежовые рукавицы:

- **Хранит список учеников**: ФИО ребёнка, контакты родителей, телефон и отметку о продлёнке;
- **Фиксирует поступления**: кто сдал деньги, сколько и когда;
- **Записывает расходы класса**: дата чека, назначение траты, за кем числится покупка и точная сумма;
- **Позволяет редактировать и удалять** учеников, платежи и расходы;
- **Ведёт несгораемый архив**: если запись удалили или изменили, триггеры базы данных бережно копируют историю в архивные таблицы (ведь перед родительским собранием каждый рубль на счету!);
- **Считает баланс в реальном времени**: внизу окна всегда видна строка: сколько всего сдано, сколько потрачено и какой текущий остаток в кассе.

### Архитектура на пальцах: никакого веба, честный десктоп

В приложении нет браузерного движка, модных REST API, контейнеров или внешнего веб-сервера. Это классический надёжный десктоп:

```text
┌──────────────────────────────┐       FireDAC / TCP/IP     ┌─────────────────┐
│ Windows-программа Delphi     │ ─────────────────────────> │ Microsoft       │
│ окна, кнопки, гриды, фреймы  │ <───────────────────────── │ SQL Server      │
└──────────────────────────────┘     строки данных и ошибки │ база "foura"    │
                                                            └─────────────────┘
```

**FireDAC** — это мощная родная библиотека Delphi для работы с базами данных. Программа подключается к SQL Server напрямую по сети или локально и общается с ним на чистом T-SQL.

## 2. Что такое `code_explorer`

Начать первое знакомство с проектом можно прямо из браузера. Загляни в папку проекта и открой:

```text
code_explorer/index.html
```

Это твой интерактивный путеводитель: слева меню модулей, по центру подсвеченный исходный код на Pascal, а если навести мышку на выделенный блок — всплывёт карточка с подробным объяснением, что этот кусок кода делает и зачем он тут нужен.

### Главное — не перепутать две вещи!

```text
Реальное приложение:
  SchoolExpensesDemo.dpr + *.pas + *.dfm
  Компилируются в Delphi IDE, работают в Windows и ходят в реальный SQL Server.

Учебный просмотрщик:
  code_explorer/index.html + app.js + files/*.js
  Открываются браузером для обучения и к базе данных сами не подключаются.
```

### Как устроен просмотрщик изнутри

В файлах вроде `code_explorer/files/uDb.js` лежит JSON-подобная структура:

```javascript
window.LEARN_FILES['uDb'] = {
  code: `unit uDb; ...`,
  annotations: [
    {
      startLine: 1,
      endLine: 8,
      title: 'Подключение к базе данных',
      explanation: 'Здесь настраиваются параметры TFDConnection...'
    }
  ]
};
```

То есть Pascal-код внутри JS-файла сохранён как обычная текстовая строка. Движок `app.js`:
1. собирает все файлы из реестра `window.LEARN_FILES`;
2. строит список в боковом меню;
3. разбивает текст на строки;
4. подсвечивает синтаксис Pascal с помощью библиотеки Prism.js;
5. оборачивает нужные диапазоны строк в интерактивные блоки;
6. показывает подсказку при наведении курсора.

Меню в `app.js` специально выстроено «снизу вверх» — от фундамента (база данных) к крыше (пользовательский интерфейс):

```text
uDb                 ➔ фундамент: физическое соединение с сервером
uMigrations         ➔ строитель: создание таблиц и триггеров
uRepositories       ➔ работяги: прямые SQL-запросы к таблицам
uServices           ➔ фейсконтроль: бизнес-правила и проверки
uMainData           ➔ табло данных: SELECT-запросы для экранных сеток
uUiHelpers          ➔ швейцарский нож: парсинг сумм, комбобоксы
uBaseEditForm       ➔ базовый шаблон формы редактирования
uUpdatePupilForm    ➔ окно редактирования ученика
uUpdatePaymentForm  ➔ окно редактирования платежа
uUpdateExenseForm   ➔ окно редактирования расхода (да-да, с опечаткой Exense!)
uMainForm           ➔ главное окно-дирижёр
uPupilsFrame        ➔ вкладка учеников
uPaymentsFrame      ➔ вкладка платежей
uExpensesFrame      ➔ вкладка расходов
uArchiveFrame       ➔ вкладка архива
```

> 💡 **Приятельский совет**: `code_explorer` — это статическая учебная копия. Если ты отредактируешь `.pas` файл в корне проекта, браузерный просмотрщик сам по волшебству не обновится, пока ты не актуализируешь соответствующий `.js` файл.

## 3. Минимум Delphi, который нужен для понимания

Если ты раньше писал на C#, Java, Python или JavaScript, некоторые вещи в Delphi могут показаться непривычными. Давай быстро снимем все вопросы на жизненных аналогиях.

### 3.1. Файл проекта `.dpr` — главный режиссёр

Файл `SchoolExpensesDemo.dpr` — это точка входа, аналог функции `main()` в C++/Java или `if __name__ == '__main__':` в Python. В нём Delphi видит:
- имя программы (`program SchoolExpensesDemo;`);
- список подключённых модулей (`uses ...`);
- стартовый код, который выполняется в первую очередь;
- создание начальных объектов.

В классических простых примерах из учебников `.dpr` выглядит очень коротко:

```pascal
program SchoolExpensesDemo;

uses
  Vcl.Forms,
  uMainForm in 'uMainForm.pas';

begin
  Application.Initialize;
  Application.Run;
end.
```

В нашем проекте `.dpr` ощутимо длиннее, потому что он выступает в почётной роли **Composition Root (Точки сборки)** — места, где создаются и соединяются между собой все зависимости приложения (база ➔ репозитории ➔ сервисы ➔ экранные формы).

### 3.2. Модуль `.pas` — витрина и кухня

Каждый `.pas` — это модуль (`unit`), самостоятельный строительный блок программы:

```pascal
unit uServices;

interface

// 1. ВИТРИНА (Публичные объявления)
// Всё, что объявлено здесь, видят другие модули, подключившие uServices в uses.

implementation

// 2. КУХНЯ (Внутренняя реализация)
// Здесь пишется реальный код методов. Внутренние переменные и служебные штуки
// отсюда наружу не торчат.

end.
```

Аналогия из жизни: `interface` — это меню в зале ресторана с названиями блюд и ценами, а `implementation` — закрытая служебная кухня с кастрюлями, рецептами и секретами повара.

Секция `uses` — это список модулей, чьи типы и функции нам нужны для работы. Забыл прописать модуль в `uses` — компилятор Delphi тут же вежливо возмутится: *«E2003 Undeclared identifier»*.

### 3.3. Класс и объект: рецепт и пирог

- **Класс** (`type TSchoolDb = class`) — это чертёж дома или кулинарный рецепт пирога.
- **Объект** (`Db: TSchoolDb`) — это реальный дом из кирпича или свежеиспечённый пирог на столе.

```pascal
Db := TSchoolDb.Create;  // Создали объект (выделили память)
try
  Db.Connect;            // Вызвали метод
finally
  Db.Free;               // Освободили объект и вернули память системе
end;
```

В классическом Delphi нет фонового сборщика мусора (Garbage Collector), как в Java или JavaScript. Поэтому действует железное джентльменское правило: **«Сам создал через `.Create` — сам и убери за собой через `.Free`»**. А связка `try...finally` гарантирует, что память освободится даже в случае внезапной ошибки.

### 3.4. Форма и `.dfm` — логика и шкурка

Окно в VCL почти всегда состоит из неразлучной пары файлов:
- `uMainForm.pas` ➔ код на Pascal: класс формы, переменные, логика и обработчики кликов;
- `uMainForm.dfm` ➔ текстовый чертёж внешности: какие кнопки, списки, какого размера и на каких координатах лежат.

В коде Pascal есть специальная директива:

```pascal
{$R *.dfm}
```

Она указывает компилятору: *«Прикрепи к этому модулю одноимённый `.dfm` как ресурс»*. Поэтому когда управление доходит до твоего кода, компоненты вроде `StatusLabel`, `PageControl` и `PupilsTab` уже реально созданы дизайнером и готовы к работе.

### 3.5. Событие: жизнь по звонку в дверь

Программы на Delphi не несутся сверху вниз до конца, а живут в режиме ожидания событий. Кнопка ждёт клика (`OnClick`), таблица ждёт двойного клика (`OnDblClick`), окно ждёт попытки закрытия (`OnClose`):

```pascal
procedure TPupilsFrame.AddPupilClick(Sender: TObject);
begin
  // Код проснётся и выполнится только тогда, когда юзер нажмёт кнопку
end;
```

Параметр `Sender` — это «виновник торжества». В нём передаётся ссылка на тот компонент, который вызвал событие (чаще всего это конкретная кнопка или таблица).

### 3.6. Фрейм (`TFrame`): модульные комнаты вместо сарая

`TFrame` — это маленькая визуальная панель со своими кнопками и полями, которую можно как модуль встроить внутрь большой формы.

Представь, что ты строишь квартиру. Вместо того чтобы свалить кровать, плиту, душ и стиральную машину в одну гигантскую кучу в зале (в программировании такой антипаттерн называют **God Object** — «Божественный объект», который делает всё на свете), ты делаешь отдельные удобные комнаты.

В нашем проекте каждая вкладка — это отдельный фрейм:

```text
TMainForm (Главное окно)
├── TPupilsFrame   (Вкладка учеников)
├── TPaymentsFrame (Вкладка платежей)
├── TExpensesFrame (Вкладка расходов)
└── TArchiveFrame  (Вкладка архива)
```

Благодаря этому `uMainForm.pas` остаётся чистым, компактным и понятным, а не превращается в 5000-строчное полотно.

## 5. Главная архитектурная схема

Давай посмотрим, как данные путешествуют по слоям нашего приложения. Это очень похоже на работу слаженного ресторана:

```text
                         Пользователь (Клиент ресторана)
                                      │
                   клики, двойные клики, ввод текста в поля
                                      │
                                      ▼
┌───────────────────────────────────────────────────────────────┐
│ СЛОЙ UI (uMainForm + фреймы + модальные формы)                │
│ Что видит юзер: кнопки, поля Edit, ComboBox, гриды TDBGrid    │
└───────────────────────────────────────────────────────────────┘
             │                                  ▲
             │ 1. Изменить данные               │ 4. Показать данные
             ▼                                  │
┌──────────────────────────────┐    ┌──────────────────────────┐
│ uServices (Бизнес-логика)    │    │ uMainData (Данные гридов)│
│ Проверка и строгие правила   │    │ 5x SELECT + TFDQuery     │
│ «Менеджер зала / контроль»   │    │ «Электронное табло зала» │
└──────────────────────────────┘    └──────────────────────────┘
             │                                  ▲
             │ 2. Выполнить SQL                 │ 3. Перечитать SELECT
             ▼                                  │
┌──────────────────────────────┐    ┌──────────────────────────┐
│ uRepositories (Репозитории)  │    │ 5x TDataSource           │
│ INSERT / UPDATE / DELETE     │    │ «Переходники к розетке»  │
│ «Повара на кухне»            │    └──────────────────────────┘
└──────────────────────────────┘                 ▲
             │                                   │
             │                                   │ связывает с
             │                                   ▼
             │                              TDBGrid на экране
             │
             ▼
┌───────────────────────────────────────────────────────────────┐
│ Общий канал TFDConnection (uDb)                               │
│ «Одна надёжная телефонная линия к базе данных»                │
└───────────────────────────────────────────────────────────────┘
                               │
                               ▼
               SQL Server / База данных "foura"
```

Сбоку инфраструктурный слой готовит этот общий канал при старте:

```text
uDb.Connect       ➔ подключиться к SQL Server и проверить наличие базы
uDb.Migrate       ➔ позвать строителя uMigrations
uMigrations       ➔ создать недостающие таблицы и триггеры
```

### Разделение труда:
- **UI (Официант)**: принимает заказ от пользователя, но сам не готовит и в базу не лезет.
- **Сервис (Администратор/Менеджер)**: проверяет, корректен ли заказ (сумма положительная? имя заполнено?).
- **Репозиторий (Повар)**: знает точный SQL-рецепт и сохраняет данные в базу.
- **`uMainData` (Табло заказов)**: делает выборку `SELECT` и обновляет картинку на экране.

## 6. Что происходит при запуске (пошаговый детектив)

Давай откроем файл `SchoolExpensesDemo.dpr` и построчно проследим, как приложение просыпается и шаг за шагом собирает себя.

### 6.1. Начало `.dpr` и локальные переменные

В реальном `SchoolExpensesDemo.dpr` объявлены переменные:

```pascal
var
  Db: TSchoolDb;
  Pupils: TPupilRepository;
  Payments: TPaymentRepository;
  Expenses: TExpenseRepository;
  PupilSvc: TPupilService;
  PaymentSvc: TPaymentService;
  ExpenseSvc: TExpenseService;
  Balance: TBalanceService;
  MainData: TMainData;
```

Это не глобальные переменные формы. Это временные рабочие переменные точки сборки, которые нужны, чтобы последовательно создать объекты, передать их друг другу и в конце аккуратно освободить память.

### 6.2. Пошаговый порядок старта

#### Шаг 1. Инициализация VCL
```pascal
Application.Initialize;
Application.MainFormOnTaskbar := True;
```
Глобальный объект `Application` просыпается, регистрирует окно в панели задач Windows и готовит цикл обработки системных сообщений.

#### Шаг 2. Создание объекта базы данных
```pascal
Db := TSchoolDb.Create;
try
  Db.Connect;
```
`TSchoolDb.Create` создаёт компонент `TFDConnection`, но пока не открывает его. Реальное сетевое подключение открывает метод `Connect`.

#### Шаг 3. Подключение к SQL Server и проверка базы
```text
TFDConnection.Params:
  DriverID  = MSSQL       (драйвер Microsoft SQL Server)
  Server    = localhost   (локальный сервер)
  OSAuthent = Yes         (вход по Windows-аккаунту без паролей)
```

Сначала соединение открывается без указания конкретной базы данных — на уровне сервера (в системной базе `master`), чтобы выполнить хитрый SQL-запрос:

```sql
IF DB_ID(N'foura') IS NULL
    CREATE DATABASE [foura]
```

Если базы `foura` ещё не существует, сервер её создаст. Затем `TFDConnection` закрывается, получает параметр `Database = foura` и открывается заново уже напрямую в рабочей базе.

```text
localhost / master
        │
        ├──> базы foura нет? создать!
        ├──> отключиться от master
        └──> подключиться к рабочей базе foura
```

#### Шаг 4. Миграция структуры базы
```pascal
Db.Migrate;
```
Метод `TSchoolDb.Migrate` передаёт открытое соединение в строитель `TSchoolDbMigrator.Migrate(FConnection)`.

Мигратор:
1. открывает SQL-транзакцию;
2. создаёт отсутствующие таблицы (`parents_and_children`, `money_from_parents`, `outlay`);
3. создаёт или обновляет архивные триггеры;
4. фиксирует изменения (`Commit`);
5. если произошла ошибка — делает откат (`Rollback`) и выбрасывает понятное исключение.

#### Шаг 5. Создание репозиториев
```pascal
Pupils := TPupilRepository.Create(Db.Connection);
Payments := TPaymentRepository.Create(Db.Connection);
Expenses := TExpenseRepository.Create(Db.Connection);
```
Все три репозитория получают **один и тот же `Db.Connection`**. Это не три разных сетевых подключения, а три мастера, работающие через одну общую надёжную «трубу» к SQL Server.

#### Шаг 6. Создание сервисов (Dependency Injection)
```pascal
PupilSvc := TPupilService.Create(Pupils);
PaymentSvc := TPaymentService.Create(Payments);
ExpenseSvc := TExpenseService.Create(Expenses);
Balance := TBalanceService.Create(Payments, Expenses);
```
Здесь работает классическое **внедрение зависимостей (Dependency Injection)**. Сервисам не нужно самим подключаться к базе или искать репозитории — готовые репозитории передаются им прямо в конструктор.

#### Шаг 7. Подготовка витрины данных
```pascal
MainData := TMainData.Create(Db.Connection);
```
`TMainData` создаёт 5 запросов `TFDQuery` и 5 адаптеров `TDataSource`. Сами SQL-запросы пока спят — они откроются чуть позже при первом вызове `RefreshData`.

#### Шаг 8. Рождение главной формы и вызов `Init`
```pascal
Application.CreateForm(TMainForm, MainForm);
MainForm.Init(PupilSvc, PaymentSvc, ExpenseSvc, Balance, MainData);
```
`Application.CreateForm` создаёт форму стандартным VCL-механизмом. Сразу после этого обычным методом `Init` форме передаются все готовые сервисы и модуль данных.

Это намного чище и надёжнее старых подходов, когда форма сама создавала базу и репозитории внутри своего конструктора.

#### Шаг 9. Создание фреймов вкладок
Метод `MainForm.Init` вызывает процедуру `CreateFrames`:

```text
CreateFrames
  │
  ├──> TPupilsFrame.Create(Self)    (создаёт вкладку учеников)
  ├──> TPaymentsFrame.Create(Self)  (создаёт вкладку платежей)
  ├──> TExpensesFrame.Create(Self)  (создаёт вкладку расходов)
  └──> TArchiveFrame.Create(Self)   (создаёт вкладку архива)
```

Каждый фрейм получает только те сервисы, которые ему действительно нужны, и подключает свои экранные сетки к соответствующим источникам данных.

#### Шаг 10. Первое обновление данных
Метод `Init` торжественно завершается вызовом `RefreshData(nil)`:

```pascal
FMainData.RefreshData;
FPupilsFrame.RefreshView;
FPaymentsFrame.RefreshView;
FExpensesFrame.RefreshView;
FArchiveFrame.RefreshView;
UpdateStatus;
```

Сетки заполняются строками из базы данных, выпадающие списки наполняются учениками, а внизу окна рассчитывается стартовый баланс.

#### Шаг 11. Бесконечный цикл ожидания
```pascal
Application.Run;
```
Всё настроено! Программа входит в цикл ожидания событий:

```text
Ждать событие от Windows
   │
   ├──> клик по кнопке?       ➔ вызвать OnClick
   ├──> двойной клик по строке? ➔ вызвать OnDblClick
   ├──> закрытие окна?        ➔ вызвать OnClose и выйти
   └──> снова мирно ждать
```

## 7. Слой базы: `uDb` и `uMigrations`

### 7.1. Класс `TSchoolDb`

Публичный интерфейс класса подключения очень лаконичен:

```pascal
TSchoolDb = class
private
  FConnection: TFDConnection;
public
  constructor Create;
  destructor Destroy; override;
  procedure Connect;
  procedure Migrate;
  property Connection: TFDConnection read FConnection;
end;
```

Внешний код пользуется свойством `Connection`, но не лезет во внутренние настройки драйвера и не пытается открыть второе соединение.

### 7.2. Почему `uDb` и `uMigrations` разделены?

Потому что это две совершенно разные зоны ответственности:

```text
uDb.pas
  «КАК физически подключиться к серверу?» (драйвер, логин, порт, хост)

uMigrations.pas
  «ЧТО именно должно лежать внутри базы?» (какие таблицы, колонки, триггеры)
```

Если свалить это в один файл, получится гремучая смесь из параметров сокетов и многостраничных SQL-скриптов.

### 7.3. Идемпотентность: принцип кнопки лифта

Операция называется **идемпотентной**, если повторный её вызов даёт ровно тот же результат и ничего не ломает. Как кнопка вызова лифта: сколько раз на неё ни нажимай, лифт просто приедет, а не вызовет десять кабин сразу.

Таблицы в миграции создаются с предварительной проверкой:

```sql
IF OBJECT_ID(N'dbo.outlay', N'U') IS NULL
    CREATE TABLE dbo.outlay (...)
```

А триггеры создаются через современную конструкцию T-SQL:

```sql
CREATE OR ALTER TRIGGER dbo.delete_from_outlay
ON dbo.outlay
AFTER DELETE
AS
BEGIN
  ...
END
```

> ⚠️ **Важная деталь**: текущая простая миграция не сравнивает существующие колонки с новыми. Если таблица `outlay` уже существует, скрипт не станет автоматически добавлять в неё новые поля.

## 8. Как устроена база данных `foura`

Схема базы данных досталась нам из реальной жизни, поэтому в ней есть как логичные решения, так и забавные исторические артефакты.

### 8.1. Таблица учеников: `parents_and_children`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `INT NOT NULL` | Идентификатор ученика |
| `children_name` | `VARCHAR(50)` | ФИО ребёнка |
| `parent_name` | `VARCHAR(50)` | ФИО родителя |
| `phone` | `VARCHAR(20)` | Контактный телефон |
| `after_lesson` | `VARCHAR(50)` | Информация о продлёнке («Да» / «Нет» / комментарий) |

### 8.2. Таблица платежей: `money_from_parents`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `INT` | Идентификатор ученика (он же выступает ключом платежа!) |
| `children_name` | `VARCHAR(50)` | Сохранённое имя ребёнка |
| `summ_to_first_november` | `INT` | Сумма сданных денег |

Название колонки `summ_to_first_november` («Сумма к первому ноября») — прекрасный пример того, как реальная жизненная задача (сбор денег к празднику 1 ноября) увековечивается в схеме базы данных!

Обрати внимание: у платежа **нет собственного уникального id**. Поле `id` здесь хранит номер ученика. Поэтому методы `CurrentPaymentId` и `CurrentPaymentPupilId` в `TMainData` возвращают одно и то же число.

### 8.3. Таблица расходов: `outlay`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `INT IDENTITY(1,1)` | Автоинкрементный номер чека/расхода (база нумерует сама: 1, 2, 3...) |
| `date_purchaise` | `VARCHAR(20)` | Дата покупки (с исторической опечаткой `purchaise`) |
| `item_name` | `VARCHAR(100)` | Назначение покупки («Шторы в класс», «Мел и тряпки») |
| `customer` | `INT` | Номер ученика, связанного с расходом |
| `summ` | `DECIMAL(7,2)` | Точная сумма расхода с копейками |

### 8.4. Архивные таблицы

```text
money_from_parents_arc ➔ старая версия изменённого или удалённого платежа + дата архивации date_ins
outlay_arc             ➔ удалённая строка расхода
```

### 8.5. Связи между таблицами

В логике приложения связи выглядят так:

```text
parents_and_children.id = money_from_parents.id
parents_and_children.id = outlay.customer
```

В SQL-миграции явные ограничения `FOREIGN KEY` не объявлены. База доверяет коду приложения и не запрещает удалять ученика, даже если по нему числятся расходы.

## 9. Репозитории: как правильно класть данные в базу

Репозиторий — это класс, чья единственная обязанность — виртуозно выполнять SQL-запросы к одной конкретной таблице.

```text
TPupilRepository   ➔ заведует таблицей parents_and_children
TPaymentRepository ➔ заведует таблицей money_from_parents
TExpenseRepository ➔ заведует таблицей outlay
```

### 9.1. Интерфейс как трудовой договор

Интерфейс в Delphi — это строгий контракт:

```pascal
IPaymentRepository = interface
  procedure Add(APupilId: Integer; const AChildrenName: string; ASum: Currency);
  procedure Delete(AId: Integer);
  procedure Update(AId: Integer; const AChildrenName: string; ASum: Currency);
  function Total: Currency;
end;
```

Он говорит: *«Мне всё равно, как именно ты будешь сохранять данные — хоть в SQL Server, хоть в облако, хоть в текстовый файл для юнит-тестов. Главное, чтобы у тебя были эти методы с такими параметрами»*.

### 9.2. Добавление ученика: цепочка вызовов

Когда пользователь нажимает кнопку во вкладке учеников, запускается эстафета:

```text
TPupilsFrame.AddPupilClick (Пользователь нажал кнопку)
       │
       ▼
TPupilService.Add (Сервис проверяет: имя не пустое?)
       │
       ├──> Trim(FIO) = '' ? Выбросить EValidationException!
       │
       ▼
IPupilRepository.Add (Контракт репозитория)
       │
       ▼
TPupilRepository.Add (Реализация)
       │
       ▼
TFDConnection.ExecSQL(INSERT INTO parents_and_children ...)
```

Параметризованный SQL-запрос выглядит абсолютно безопасно:

```pascal
FConnection.ExecSQL(
  'INSERT INTO parents_and_children(children_name, parent_name, phone, after_lesson) ' +
  'VALUES (:children_name, :parent_name, :phone, :after_lesson)',
  [AChildrenName, AParentName, APhone, AAfterLesson]
);
```

Значения подставляются через параметры `:имя`. Никакой склейки строк плюсиками — знаменитый маленький «Роберт '); DROP TABLE Students;--» не сможет навредить нашей базе!

### 9.3. Добавление платежа

Платёж получает номер выбранного в комбобоксе ученика, его имя и сумму:

```pascal
FPaymentSvc.Add(
  GetComboPupilId(PaymentPupilCombo),
  SelectedPupilName,
  Sum
);
```

Репозиторий выполняет:

```sql
INSERT INTO money_from_parents
  (children_name, summ_to_first_november, id)
VALUES
  (:children_name, :summ, :id)
```

`id` здесь — это номер ученика, а не отдельный новый номер платежа.

### 9.4. Добавление расхода

```sql
INSERT INTO outlay
  (date_purchaise, item_name, customer, summ)
VALUES
  (:date_purchaise, :item_name, :customer, :summ)
```

Поле `id` в этот запрос не передаётся: SQL Server сам назначит новый уникальный номер благодаря свойству `IDENTITY(1,1)`.

### 9.5. Подсчёт общей суммы

```pascal
Result := FConnection.ExecSQLScalar(
  'SELECT COALESCE(SUM(summ), 0) FROM dbo.outlay'
);
```

- `ExecSQLScalar` — специальный быстрый метод FireDAC, который выполняет запрос и возвращает ровно одно скалярное значение (число или строку).
- `COALESCE(SUM(...), 0)` — важная страховка: если таблица пустая, SQL-функция `SUM` вернёт `NULL`, а `COALESCE` превратит его в честный ноль `0`, спасая нас от ошибок.

## 10. Сервисы: строгий фейсконтроль и бизнес-правила

Если репозиторий — это трудолюбивый повар, готовый приготовить любое блюдо, то **Сервис (`uServices`)** — это строгий администратор ресторана, проверяющий заказ.

### 10.1. Сервис учеников (`TPupilService`)
Проверяет:
- при добавлении и редактировании: ФИО ребёнка не должно быть пустым;
- при изменении и удалении: id ученика должен быть положительным числом (> 0).

### 10.2. Сервис платежей (`TPaymentService`)
Проверяет:
- при добавлении: ученик выбран (id > 0), сумма больше нуля;
- при изменении: платёж выбран, сумма больше нуля;
- при удалении: платёж выбран.

### 10.3. Сервис расходов (`TExpenseService`)
Проверяет:
- ученик-плательщик выбран;
- дата заполнена;
- назначение покупки указано (не пустая строка);
- сумма strictly больше нуля;
- при редактировании: сам расход существует.

### 10.4. Почему исключение именно `EValidationException`?

```pascal
type
  EValidationException = class(Exception);
```

Когда пользователь забывает ввести сумму, сервис делает:

```pascal
raise EValidationException.Create('Укажите сумму расхода больше нуля');
```

А фрейм перехватывает его через `ShowException`:

```pascal
try
  FExpenseSvc.Add(...);
except
  on E: Exception do
    ShowException(E);
end;
```

Функция `ShowException` смотрит на тип:
- если это `EValidationException` — выводит добрую подсказку пользователю: *«Укажите сумму расхода больше нуля»*;
- если это системная ошибка базы данных — добавляет префикс: *«Ошибка: [FireDAC] Connection lost...»*.

### 10.5. Расчёт баланса

```text
Баланс = Сумма всех поступлений - Сумма всех расходов
```

В коде сервиса:

```pascal
function TBalanceService.Balance: Currency;
begin
  Result := FPayments.Total - FExpenses.Total;
end;
```

Форма не считает баланс вручную и не знает формул — она просто спрашивает готовый результат у `TBalanceService`.

## 11. `uMainData`: как данные попадают в грид

### 11.1. Пять верных запросов

Модуль `TMainData` держит 5 постоянных запросов `TFDQuery`:

| Запрос | Назначение |
|---|---|
| `PupilsQuery` | Выбрать список всех учеников |
| `PaymentsQuery` | Выбрать все поступления денег |
| `ExpensesQuery` | Выбрать расходы с подтягиванием имени ученика через `LEFT JOIN` |
| `PaymentsArcQuery` | Выбрать архив изменённых и удалённых платежей |
| `ExpensesArcQuery` | Выбрать архив удалённых расходов |

У каждого запроса есть свой адаптер `TDataSource`:

```text
PupilsQuery      ➔ PupilsSource      ➔ PupilsGrid (на вкладке учеников)
PaymentsQuery    ➔ PaymentsSource    ➔ PaymentsGrid (на вкладке платежей)
ExpensesQuery    ➔ ExpensesSource    ➔ ExpensesGrid (на вкладке расходов)
PaymentsArcQuery ➔ PaymentsArcSource ➔ PaymentsArcGrid (в архиве)
ExpensesArcQuery ➔ ExpensesArcSource ➔ ExpensesArcGrid (в архиве)
```

### 11.2. Что такое `TDataSource`?

Представь розетку в стене и вилку от ноутбука:

```text
TFDQuery    = электричество и данные в стене (SQL-запрос)
TDataSource = переходник-адаптер питания
TDBGrid     = сам ноутбук с экраном (визуальная сетка)
```

Экранная таблица `TDBGrid` не умеет напрямую выполнять SQL. Ей достаточно указать переходник:

```pascal
ExpensesGrid.DataSource := FMainData.ExpensesSource;
```

### 11.3. Процесс обновления (`RefreshData`)

Когда мы добавили новый расход, запросы на экране всё ещё показывают старые строки. Чтобы обновить картинку, метод `TMainData.RefreshData` делает:

```pascal
FPupilsQuery.Close;
FPaymentsQuery.Close;
FExpensesQuery.Close;
FPaymentsArcQuery.Close;
FExpensesArcQuery.Close;

FPupilsQuery.Open;
FPaymentsQuery.Open;
FExpensesQuery.Open;
FPaymentsArcQuery.Open;
FExpensesArcQuery.Open;

ConfigureFields;
```

Команда `.Open` отправляет `SELECT` заново. Через адаптеры `TDataSource` все таблицы на экране мгновенно перерисовываются свежими данными.

### 11.4. Свойства `Current...` — прячем кишки базы

Вместо того чтобы писать во фрейме хрупкий и некрасивый код:

```pascal
FMainData.PupilsQuery.FieldByName('children_name').AsString;
```

мы сделали в `TMainData` элегантные свойства:

```pascal
FMainData.CurrentPupilName;
FMainData.CurrentPupilId;
FMainData.CurrentExpenseSum;
```

Технические имена полей базы спрятаны внутри `uMainData`. Если завтра колонка `children_name` в базе будет переименована в `fio_student`, мы поправим одну строчку в `uMainData`, а десятки экранных форм продолжат работать без изменений!

### 11.5. Настройка колонок (`ConfigureFields`)

После открытия запроса метод `ConfigureFields` наводит красоту:
- задаёт русские заголовки колонок (`DisplayLabel`), например: `item_name` ➔ **«На что потрачено»**;
- настраивает ширину столбцов (`DisplayWidth`), чтобы текст не обрезался;
- скрывает технические числовые идентификаторы (`Visible := False`).

## 12. `uMainForm`: дирижёр оркестра

Главная форма содержит:
- компонент вкладок `PageControl`;
- вкладки `PupilsTab`, `PaymentsTab`, `ExpensesTab`, `ArchiveTab`;
- нижнюю строку статуса `StatusLabel`.

Она получает зависимости через метод `Init`:

```pascal
procedure TMainForm.Init(
  APupilSvc: TPupilService;
  APaymentSvc: TPaymentService;
  AExpenseSvc: TExpenseService;
  ABalance: TBalanceService;
  AMainData: TMainData);
```

Главная форма не знает структуры таблиц SQL и сама не выполняет ни одного `INSERT` или `DELETE`.

### Почему это в сто раз лучше, чем один огромный класс?

Если бы мы по старинке свалили всё в `uMainForm.pas`, там одновременно оказались бы:
- обработка добавления учеников;
- валидация платежей и подсчёт сумм;
- форматирование дат чеков расходов;
- работа с комбобоксами;
- вызов модальных окон;
- сырые SQL-запросы;
- логика триггеров архива.

Разобраться в такой каше через месяц было бы невозможно. Сейчас у каждого своя роль:

```text
uPupilsFrame    ➔ логика и кнопки вкладки учеников

uArchiveFrame   ➔ только спокойное отображение двух таблиц архива
```

## 13. Фреймы по отдельности

### 13.1. Вкладка учеников (`TPupilsFrame`)

Хранит ссылки:
```pascal
FPupilSvc: TPupilService;
FMainData: TMainData;
FOnRefresh: TNotifyEvent;
```

При инициализации фрейм подключает сетку к источнику:
```pascal
PupilsGrid.DataSource := FMainData.PupilsSource;
```

- **Добавление**: читает 4 поля `Edit.Text` ➔ зовёт `FPupilSvc.Add` ➔ очищает поля ввода ➔ дёргает общее обновление `FOnRefresh(Self)`.
- **Удаление**: спрашивает подтверждение `ConfirmDelete('Удалить ученика?')` ➔ при согласии вызывает `FPupilSvc.Delete(FMainData.CurrentPupilId)` ➔ обновляет экран.
- **Редактирование по двойному клику**:
  1. проверяет, что в таблице есть строки;
  2. читает `CurrentPupilId` и текущие значения через `TMainData`;
  3. создаёт окно `TuEditPupilForm`;
  4. вызывает `ShowModal`;
  5. если юзер нажал «ОК» (`mrOk`), вызывает `FPupilSvc.Update(...)`;
  6. в блоке `finally` уничтожает форму;
  7. дёргает общее обновление данных.

### 13.2. Вкладка платежей (`TPaymentsFrame`)

Зависимости фрейма:
```pascal
FPaymentSvc: TPaymentService;
FPupilSvc: TPupilService;
FMainData: TMainData;
FOnRefresh: TNotifyEvent;
```

Зачем здесь два сервиса? Платёж сохраняется через `TPaymentService`, но чтобы наполнить выпадающий список `ComboBox` актуальными учениками, нужен метод `TPupilService.ListForCombo`.

### 13.3. Как комбобокс прячет `id` ученика

Пользователь видит в выпадающем списке красивый текст:
```text
Вика Крошкина
Иван Фомичев
Егор Чулков
```

Но базе данных для записи нужен числовой `id = 3`! В Delphi каждый элемент списка `TComboBox` умеет хранить не только строку, но и привязанный объект (`TObject`).

В модуле `uUiHelpers` объявлен мини-класс:

```pascal
type
  TPupilComboItem = class
  public
    Id: Integer;
    constructor Create(AId: Integer);
  end;
```

Когда комбобокс заполняется:
```pascal
ACombo.Items.AddObject(ADisplayName, TPupilComboItem.Create(APupilId));
```

А когда нужно узнать id выбранного ученика:
```pascal
Item := ACombo.Items.Objects[ACombo.ItemIndex] as TPupilComboItem;
Result := Item.Id;
```

> 🧹 **Внимание, память!** `TComboBox` сам по себе эти прикреплённые объекты не удаляет. Поэтому перед каждым пересозданием списка и в деструкторах фреймов вызывается специальная процедура `ClearComboObjects(Combo)`. Она пробегает по всем элементам, освобождает память каждого `TPupilComboItem` и только потом очищает список. Память защищена от утечек!

### 13.4. Вкладка расходов (`TExpensesFrame`)

Похожа на вкладку платежей, но полей больше: выпадающий список учеников, поле даты, назначение покупки и сумма.

При старте поле даты автоматически заполняется сегодняшним днём через `TodayIso` (например, `2026-08-19`). После успешного добавления поле назначения и суммы очищаются, а дата остаётся заполненной — ведь за один день часто вносят несколько чеков подряд.

### 13.5. Вкладка архива (`TArchiveFrame`)

Самый умиротворённый фрейм проекта:
```pascal
PaymentsArcGrid.DataSource := AMainData.PaymentsArcSource;
ExpensesArcGrid.DataSource := AMainData.ExpensesArcSource;
```
У него нет сервисов и кнопок добавления. Он просто выводит результат автоматической работы триггеров базы данных.

## 14. Формы редактирования и визуальное наследование

В проекте есть три модальных окна для изменения записей. Здесь во всей красе раскрывается мощь **Visual Form Inheritance (Визуального наследования форм)**.

### 14.1. Общий предок `TBaseEditForm`

Базовая форма содержит:
```text
Edit1 + Label1  ➔ по умолчанию дата
Edit2 + Label2  ➔ по умолчанию назначение
Edit3 + Label3  ➔ сумма
Button1         ➔ кнопка ОК
```

Конструктор принимает стартовые значения:

```pascal
constructor Create(
  AOwner: TComponent;
  const ADate, APurpose, ASum: string);
```

После вызова `inherited Create(AOwner)` все компоненты из файла `.dfm` уже созданы в памяти, и конструктор спокойно заполняет поля текстом.

### 14.2. Виртуальные методы — точки расширения

```pascal
procedure ApplyCaption; virtual;
procedure ApplyHints; virtual;
procedure ApplyLabels; virtual;
function Validate: Boolean; virtual;
function ValidateSum: Boolean; virtual;
function GetOperationType: string; virtual;
function GetPupilId: Integer; virtual;
```

Ключевое слово `virtual` означает: *«Потомки могут переопределить этот метод через `override` и сделать по-своему»*.

```text
Базовая форма TBaseEditForm задаёт общий каркас
  │
  ├──> Форма платежа скрывает лишние поля и меняет правила проверки
  └──> Форма расхода использует базовую валидацию и добавляет выбор ученика
```

### 14.3. Окно редактирования платежа (`TuEditPaymentForm`)

Наследуется от `TBaseEditForm` и добавляет:
```pascal
PupilCombo: TComboBox;
PupilLabel: TLabel;
```

Поскольку у платежа нет даты и назначения, форма делает поля `Edit1` и `Edit2` невидимыми (`Visible = False`), а проверяет только выбор ученика и положительность суммы.

### 14.4. Окно редактирования расхода (`TuEditExpenseForm`)

Также наследуется от `TBaseEditForm` и добавляет выпадающий список учеников `PupilCombo`. Расход использует все три поля. Его метод `Validate` сначала проверяет ученика, а затем вызывает:

```pascal
inherited Validate
```

Так одной строчкой переиспользуются проверки даты, назначения и суммы из базового класса!

### 14.5. Окно редактирования ученика (`TuEditPupilForm`)

Создано отдельно и наследуется напрямую от `TForm`:

Оно ничего не знает о сервисах и репозиториях: принимает строки в конструкторе, а после закрытия по «ОК» отдаёт введённый текст через методы-геттеры (`GetFullName`, `GetParentName` и т.д.).

## 15. Подробные жизненные сценарии работы

### 15.1. Добавление ученика

Пользователь заполняет 4 поля на первой вкладке и нажимает «Добавить ученика»:

```text
1. TPupilsFrame.AddPupilClick
2. Прочитать текст из 4 полей Edit
3. TPupilService.Add
4. Проверить ФИО на пустоту
5. TPupilRepository.Add
6. FConnection.ExecSQL(INSERT INTO parents_and_children ...)
7. Очистить поля ввода
8. Вызвать MainForm.RefreshData
9. Перечитать 5 запросов TFDQuery
10. Обновить таблицы на экране и пересчитать баланс
```

> ⚠️ **Важный нюанс учебной схемы**: в исходной миграции колонка `id` таблицы учеников создана как обязательный `INT NOT NULL`, но без свойства `IDENTITY`. Поскольку метод `Add` не передаёт значение `id`, этот запрос завершится ошибкой SQL Server. Подробнее о причинах и решениях мы поговорим в разделе 19.

### 15.2. Добавление платежа

```text
Пользователь выбрал в списке: «Иван Фомичев» и ввёл сумму «2450»
                               │
                               ▼
ParseSum('2450', Currency) ➔ успешно получили 2450.00
                               │
                               ▼
GetComboPupilId ➔ узнали id ученика = 3
                               │
                               ▼
TPupilService.PupilNameById(3) ➔ получили строку «Иван Фомичев»
                               │
                               ▼
TPaymentService.Add(3, 'Иван Фомичев', 2450)
                               │
                               ▼
TPaymentRepository.Add
                               │
                               ▼
INSERT INTO money_from_parents (children_name, summ_to_first_november, id)
VALUES ('Иван Фомичев', 2450, 3)
```

После вставки вызывается общий `RefreshData`, и сумма мгновенно отображается в таблице и строке статуса.

### 15.3. Добавление расхода (Покупка штор!)

1. Пользователь выбирает ответственного ученика из выпадающего списка.
2. Поле даты уже заполнено сегодняшним днём (`2026-08-19`).
3. Пользователь пишет назначение: *«Шторы в класс»* и сумму *«15400»*.
4. `ParseSum` аккуратно преобразует строку в денежный тип `Currency`.
5. `TExpenseService` проверяет корректность всех полей.
6. `TExpenseRepository` отправляет `INSERT INTO outlay`.
7. SQL Server генерирует новый `id` покупки через `IDENTITY`.
8. `MainForm.RefreshData` обновляет экран и вычитает 15 400 рублей из баланса.

### 15.4. Редактирование расхода

```text
Двойной клик по строке расхода в таблице
         │

Прочитать значения текущей строки из TMainData:

         │
         ▼

         ├──> заполнить поля Edit
         ├──> наполнить PupilCombo учениками

         ▼

```

Блок `try...finally` гарантирует, что модальное окно и связанные с ним объекты комбобокса будут уничтожены в любом случае.

### 15.5. Удаление платежа и срабатывание триггера-архивариуса

```text
Нажать кнопку «Удалить платёж»
         │
         ▼

         │
         ├──> Нет: спокойно выйти
         │
         └──> Да:
               │

               │
               ▼

               │
```

Программа не вставляет строки в архив вручную — это полностью берёт на себя SQL Server.

### 15.6. Изменение платежа и сохранение истории

При выполнении `UPDATE money_from_parents` триггер `money_from_parents_update` перехватывает старые значения из служебной псевдотаблицы `deleted` и отправляет их в архив. Поэтому в архиве остаётся история «как было до изменения», а в рабочей таблице живёт новая версия.

## 16. Обработка ошибок без паники

Типичный обработчик любого действия на форме выглядит так:

```pascal
try
  FExpenseSvc.Add(...);
  FOnRefresh(Self);
except
  on E: Exception do
    ShowException(E);
end;
```

Обрати внимание на строгий порядок:
1. сначала выполняем операцию в базе;
2. **только в случае полного успеха** обновляем экран и очищаем поля;
3. если база упала с ошибкой — блок `except` перехватит её и покажет сообщение пользователю, а введённый текст в полях не сотрётся!

Процедура `ShowException` в `uUiHelpers` аккуратно разделяет ошибки:
- `EValidationException` ➔ показывает понятную подсказку (*«Выберите ученика из списка»*);
- любые другие системные ошибки ➔ выводят понятный технический текст с префиксом *«Ошибка: »*.

## 17. Суммы и почему тип `Currency` — лучший друг финансов

В Delphi для работы с денежными суммами всегда используется тип **`Currency`**:

```pascal
var
  Sum: Currency;
```

### Почему нельзя использовать обычный `Double` или `Single`?
Числа с плавающей точкой хранятся в двоичном виде. Простое сложение `0.1 + 0.2` в типе `Double` может дать `0.30000000000000004`! В финансовых расчётах потеря даже одной копейки на родительском собрании может вызвать грандиозный скандал.

Тип `Currency` в Delphi:
- это число с фиксированной точкой (ровно 4 знака после запятой);
- операции сложения и вычитания абсолютно точны;
- красивый вывод на экран делается через спецификатор `%m`:

```pascal
Format(
  'Сдано: %m   Потрачено: %m   Баланс: %m',
  [FPaymentSvc.Total, FExpenseSvc.Total, FBalance.Balance]
)
```

Функция `Format('%m', ...)` сама добавит знак валюты и разделители разрядов из региональных настроек Windows.

## 18. Время жизни объектов и сборка матрёшки

В файле `SchoolExpensesDemo.dpr` используется вложенная цепочка `try...finally`:

```pascal
Db := TSchoolDb.Create;
try
  // 1. Создаём репозитории (требуют Connection)
  try
    // 2. Создаём сервисы (требуют репозитории)
    try
      // 3. Создаём MainData, форму и запускаем цикл
      Application.Run;
    finally
      // 3. Освобождаем сервисы
    end;
  finally
    // 2. Освобождаем репозитории
  end;
finally
  Db.Free; // 1. Освобождаем базу в самую последнюю очередь!
end;
```

Принцип простой: **в каком порядке создавали зависимости, в строго обратном порядке их нужно освобождать**. Нельзя уничтожить объект базы данных `Db`, пока живы репозитории, иначе при попытке закрытия репозитории обратятся к уже уничтоженной памяти.

### Особенность интерфейсов в нашем проекте

Обычно в Delphi интерфейсы используют автоматический подсчёт ссылок. Но наш базовый класс `TRepository` явно реализует методы `_AddRef` и `_Release`, возвращая результат `-1`:

```pascal
function TRepository._AddRef: Integer;
begin
  Result := -1; // "Не управляй моей памятью автоматически!"
end;
```

Это сделано специально, чтобы время жизни объектов полностью и предсказуемо контролировалось точкой сборки `.dpr` через явные вызовы `.Free`.

## 19. Текущие ограничения схемы, о которых важно знать

В реальной разработке идеальных систем не бывает — у каждого проекта есть своя история развития и компромиссы. Вот честный разбор шероховатостей нашей учебной базы:

### 19.1. Поле `id` нового ученика
В миграции таблица `parents_and_children` создана с колонкой `id INT NOT NULL PRIMARY KEY`, но без автоинкремента `IDENTITY`. А в методе `TPupilRepository.Add` значение `id` не передаётся в запрос `INSERT`. Поэтому добавление нового ученика на чистой базе приведёт к ошибке SQL Server. 
> 🛠 *Как лечится в промышленном коде*: добавлением свойства `IDENTITY(1,1)` к колонке `id` в миграции.
> 🧪 *Кстати*: интеграционный тест знает об этом ограничении — в `tests/uRepositoryTests.pas` (тест `Pupil_UpdateDelete_ListForCombo`) строка ученика создаётся прямым INSERT с явным `id`, а ограничение задокументировано в комментарии.

### 19.2. `INT` для суммы платежа
В интерфейсе Delphi мы используем точный `Currency` с копейками, но историческая колонка `summ_to_first_november` создана как `INT`. Дробные суммы платежей база округлит.

### 19.3. Отсутствие внешних ключей (Foreign Keys)
Поле `outlay.customer` логически хранит id ученика, но физического ограничения `FOREIGN KEY` в базе нет. Если удалить ученика из первой вкладки, его расходы в третьей вкладке сохранятся, но `LEFT JOIN` вместо имени покажет пустую ячейку.

### 19.4. Изменение ученика у существующего платежа
Форма редактирования платежа даёт возможность выбрать другого ученика из списка. Однако метод `TPaymentService.Update` обновляет имя и сумму, но оставляет прежний `id`. В результате имя в строке может принадлежать одному ребёнку, а `id` — другому.

### 19.5. Архив расходов не хранит историю изменений
Для таблицы `outlay` настроен только триггер удаления `delete_from_outlay`. Триггера на изменение (`AFTER UPDATE`) нет, поэтому промежуточные версии отредактированных расходов в архив не попадают.

### 19.6. Дублирование валидации
Проверка сумм и обязательных полей выполняется и в экранных формах (через `ParseSum`), и повторно в сервисах. Это небольшое дублирование кода, но оно полезно: бизнес-правило остаётся защищённым, даже если форму вызовут нестандартным способом.

### 19.7. Историческая схема платежей
Поскольку `money_from_parents.id` — это id ученика, а не отдельный id платежа, один ученик может иметь только одну концептуальную запись в этой упрощённой модели.

### 19.8. Повторные платежи от одного ученика
У таблицы `money_from_parents` нет первичного ключа. Если добавить платёж на одного и того же ученика дважды, в базе появятся две записи с одинаковым `id`. А команда `DELETE WHERE id = :id` удалит сразу обе эти строки.

Знать эти нюансы очень полезно: именно на таких живых примерах лучше всего учиться проектировать правильные реляционные базы данных!

## 22. Почему не стоит писать всё в одной кнопке `Button1Click`?

Для начинающего разработчика велик соблазн написать код добавления прямо в обработчике кнопки:

```pascal
procedure TMainForm.Button1Click(Sender: TObject);
begin
  Connection.ExecSQL('INSERT INTO outlay VALUES (...)');
end;
```

Кажется: *«Зачем городить сервисы и репозитории, если в 3 строчки всё работает?»*.

Но в реальном проекте эта кнопка моментально обрастает сложностями:
- нужно проверить 5 условий ввода;
- нужно показать красивые ошибки;
- нужно заблокировать ввод при сбое сети;
- нужно обновить 3 других таблицы на соседних вкладках;
- нужно пересчитать баланс кассы;
- нужно залогировать действие.

Через пару недель файл формы раздувается до 4000 строк спагетти-кода, в котором страшно изменить даже название кнопки.

В нашей архитектуре обязанности чётко разделены:
```text
Фрейм (Frame)        ➔ знает только UI: какие поля прочитать и какое событие обработать
Сервис (Service)     ➔ знает только бизнес-правила: что разрешено, а что нет
Репозиторий (Repo)   ➔ знает только SQL-запросы к своей таблице
Данные (MainData)    ➔ знают только SELECT-выборки для отображения в сетках
База (Database)      ➔ хранит физические таблицы и гарантирует сохранность данных триггерами
```

Если завтра дизайнер захочет переделать все кнопки на круглые — мы изменим только UI. Если администратор переименует колонку в базе — мы изменим только репозиторий. Слои изолированы друг от друга!

## 25. Тесты: страховочная сетка для школьной кассы

До сих пор мы проверяли программу руками: нажали кнопку — посмотрели на грид. Но представь, что ты поменял проверку суммы в `TExpenseService.Add` и забыл про отрицательные числа. Кто тебя поймает? Правильно — тесты.

### 25.1. Как устроен тестовый проект

В папке `tests/` живёт **отдельное консольное приложение** `SchoolExpensesTests.dpr`. Оно не открывает никаких окон: просто запускает все тесты фреймворка DUnitX и печатает сводку:

```text
Done testing.
Tests Found   : 68
Tests Passed  : 68
Tests Errored : 0
```

Запуск из командной строки (каталог `tests`):

```powershell
& "C:\Program Files (x86)\Embarcadero\Studio\37.0\bin\dcc64.exe" -B SchoolExpensesTests.dpr
.\SchoolExpensesTests.exe
```

Код возврата — число, которое программа оставляет операционной системе: `0` значит «всё хорошо», `1` — «есть провалы». Именно по этому числу автоматика (или внимательный ты) понимает, зелёный ли прогон.

### 25.2. Модульные тесты: проверяем сервисы без базы данных

Помнишь главу про слои? Сервис общается с репозиторием **через интерфейс**. А раз так, настоящую базу можно заменить **моком** — двойником-подставкой из `tests/uTestMocks.pas`:

```text
Настоящая цепочка:   TExpenseService -> TExpenseRepository -> SQL Server
Цепочка в тесте:     TExpenseService -> TMockExpenseRepo   -> (ничего, просто записывает вызов)
```

Мок работает как подставной свидетель: он не ходит в базу, зато запоминает, кто, когда и с какими аргументами его вызывал (`AddCount`, `LastAddedItem`...), и возвращает заранее приготовленные ответы (`TotalToReturn` и т.п.).

Что это даёт? Тест сервиса проверяет **ровно один слой**:

```pascal
procedure TExpenseServiceTests.Add_ZeroSum_RaisesValidation;
begin
  ExpectValidationError(
    procedure begin FSvc.Add(2, '2026-09-01', 'Тетради', 0) end,
    'Сумма расхода должна быть больше нуля');
  Assert.AreEqual(0, FRepo.AddCount, 'Репозиторий не должен вызываться');
end;
```

`ExpectValidationError` — маленький помощник внутри `uServiceTests.pas`: он выполняет переданную процедуру и проверяет, что вылетела именно `EValidationException` с ожидаемым текстом. А вторая строка через мок убеждается, что до репозитория (то есть до базы) некорректный расход не дошёл.

Никакого SQL Server, никакой сети — миллисекунды на сотню таких проверок. Точно так же тестируются хелперы `uUiHelpers` (`ParseSum` и друзья) — им база и вовсе не нужна.

### 25.3. Интеграционные тесты: проверяем настоящий SQL

Моки хороши, но они верят, что SQL-запрос написан правильно. А если в `INSERT` опечатка в имени колонки? Для этого есть интеграционные тесты `tests/uRepositoryTests.pas`: они поднимают **настоящий SQL Server** и прогоняют код по-настоящему.

Два важных правила безопасности:

1. Тесты работают **не с боевой базой `foura`**, а с отдельной `foura_tests`. Она удаляется и создаётся заново при каждом прогоне — как песочница.
2. Если сервер выключен, тесты не падают: фикстура просто не регистрируется (проверка `SqlServerAvailable` при старте), и прогон остаётся зелёным. Интеграционные тесты требуют сервера, но не должны требовать его от каждого, кто правит документацию.

Что они проверяют: миграции создают все таблицы и триггеры (и повторный запуск ничего не ломает), CRUD репозиториев доходит до базы, архивация переносит строки в `*_arc` и пишет сальдо, а обёртки `TMainData` отдают правильные поля гридам.

### 25.4. Честное лицо проекта

Интеграционные тесты уже поймали одну занятную вещь: попытка добавить ученика через `TPupilRepository.Add` падает, потому что колонка `id` создана без `IDENTITY` (глава 19.1). Тест не стал делать вид, что проблемы нет, — он создаёт ученика прямым INSERT с явным `id` и оставляет комментарий с объяснением. Так тестовая база становится ещё и документацией ограничений.

### 25.5. Когда писать тесты

Каждый раз, когда меняешь интерфейс репозитория или правило в сервисе:

1. Обнови мок в `tests/uTestMocks.pas` — иначе тестовый проект просто не соберётся (мок обязан реализовать все методы интерфейса);
2. Добавь тест на новое правило: и на «хороший» сценарий, и на тот, где должна вылететь `EValidationException`;
3. Прогони `SchoolExpensesTests.exe` и убедись, что сводка зелёная.

Правило простое: **изменил слой — прогони тесты**. Это дешевле, чем объяснять родительскому комитету, куда пропали деньги из кассы.
