# Как работает SchoolExpensesDemo — подробное объяснение для новичка

> Это руководство написано для тех, кто только начинает изучать Delphi.
> Здесь простыми словами расписано: что делает программа, из каких файлов
> состоит, как эти файлы между собой общаются и в каком порядке всё происходит.

---

## 1. Что это за программа?

**SchoolExpensesDemo** — это десктопное Windows-приложение (VCL) на Delphi для
учёта школьных расходов. Оно решает простую задачу классного родительского
комитета:

- кто из детей сдал деньги в общую кассу и сколько;
- на что эти деньги потратили;
- сколько денег осталось (баланс).

Программа хранит данные в **Microsoft SQL Server** (локальном, на этом же
компьютере) и работает с базой **напрямую** через библиотеку **FireDAC** —
без веб-серверов и REST API.

```
┌─────────────────────────┐      пересылка SQL-запросов      ┌──────────────────┐
│  VCL-окно (Delphi)      │ ─────────────────────────────▶ │  SQL Server      │
│  гриды, кнопки, формы   │ ◀───────────────────────────── │  база "foura"    │
└─────────────────────────┘           ответ (таблицы)       └──────────────────┘
```

## 2. Что нужно знать о Delphi, чтобы понимать этот код

### 2.1. Программа = набор "юнитов" (модулей)

Любая Delphi-программа — это **набор файлов-модулей (.pas)** плюс один файл
точки входа **.dpr** (проект). Каждый `.pas` — это отдельный "кирпичик"
(в других языках — модуль/пакет/исходник).

У каждого модуля есть структура:

```pascal
unit ИмяМодуля;      // имя модуля (обязано совпадать с именем файла)

interface             // ПУБЛИЧНАЯ часть: что этот модуль "показывает наружу"
uses ...;             //   какие другие модули он использует
type ...;             //   какие классы/типы он предоставляет

implementation        // ПРИВАТНАЯ часть: внутренняя кухня
...
end.
```

### 2.2. Ключевые слова

| Понятие | Что это |
|---|---|
| `uses` | Список модулей, на которые ссылается текущий. Без него Delphi не найдёт чужие классы. |
| `unit` | Модуль (файл). |
| `type` | Объявление класса / типа. |
| `procedure` / `function` | Процедура (не возвращает значение) / функция (возвращает). |
| `class` | Класс — шаблон объекта. Создаётся через `.Create`, удаляется через `.Free`. |
| `inherited` | Вызов метода предка (родительского класса). |
| `override` | Переопределить виртуальный метод родителя (заменить его поведение). |
| `.dfm` | Файл с описанием формы (кто где стоит на экране). |

### 2.3. Форма = пары файлов `.pas` + `.dfm`

В VCL форма разбита на два файла:

- **`.dfm`** — *описание внешнего вида*: какие кнопки, поля, надписи и где они
  расположены (позиции, размеры, названия). Это текстовый файл, обычно его
  редактируют мышкой в дизайнере форм.
- **`.pas`** — *логика*: класс формы (`class(TForm)`), на который "навешаны"
  компоненты из `.dfm`, и код обработчиков (что происходит при нажатии кнопки
  и т.п.).

Связь: строка `{$R *.dfm}` в `.pas` говорит компилятору "присоедини мой
одноимённый `.dfm`". Строка `OnClick = AddPupilClick` в `.dfm` говорит "когда
нажмут эту кнопку — вызови метод `TMainForm.AddPupilClick`".

### 2.4. События (обработчики)

VCL работает по принципу событий: программа ничего не делает "сама по себе",
а ждёт действий пользователя (клик, двойной клик, закрытие окна) и реагирует
на них через **обработчики** — методы вида:

```pascal
procedure TMainForm.AddPupilClick(Sender: TObject);
```

`Sender` — это объект, который вызвал событие (в данном случае кнопка).

### 2.5. Классы и объекты

В программе активно используются **классы**:

```pascal
FDb := TSchoolDb.Create;          // создать объект подключения к БД
FDb.Connect;                      // вызвать его метод
FDb.Free;                         // уничтожить
```

Правило: всё, что сделали через `.Create`, обязаны освободить через `.Free`,
иначе — утечка памяти.

## 4. Как программа запускается (сценарий старта)

Разберём файл `.dpr` — это первое, что исполняется:

```pascal
program SchoolExpensesDemo;

uses
  Vcl.Forms,                       // сама библиотека форм
  uMainForm, uDb, uMigrations, ... // наши модули
{$R *.res}

begin
  Application.Initialize;                        // 1. инициализация VCL
  Application.MainFormOnTaskbar := True;
  Application.CreateForm(TMainForm, MainForm);   // 2. создать главную форму
  Application.CreateForm(TuEditExpenseForm, uEditExpenseForm); // 3. доп. форма
  Application.Run;                               // 4. запустить цикл событий
end.
```

Теперь главное. Когда создаётся главная форма, вызывается её конструктор
`TMainForm.Create` (`uMainForm.pas:118`). Внутри него происходит **вся
инициализация приложения**:

```pascal
constructor TMainForm.Create(AOwner: TComponent);
begin
  inherited Create(AOwner);        // сначала стандартная инициализация TForm

  FDb := TSchoolDb.Create;         // 1. создать объект "база данных"
  FDb.Connect;                     // 2. подключиться к SQL Server (и создать БД)
  FDb.Migrate;                     // 3. создать таблицы и триггеры, если их нет

  FPupils := TPupilRepository.Create(FDb.Connection);    // 4. репозитории
  FPayments := TPaymentRepository.Create(FDb.Connection);
  FExpenses := TExpenseRepository.Create(FDb.Connection);
  FBalance := TBalanceService.Create(FPayments, FExpenses); // 5. сервис баланса
  FMainData := TMainData.Create(FDb.Connection);        // 6. данные для гридов

  BindDataSources;                 // 7. привязать гриды к данным
  ExpenseDateEdit.Text := TodayIso; // 8. сегодняшняя дата в поле расхода
  RefreshData;                     // 9. загрузить все таблицы в гриды
end;
```

Порядок важен: **сначала база и структура, потом сервисы, потом данные**.

После этого `Application.Run` запускает бесконечный цикл обработки событий —
окно живёт, пока пользователь его не закроет. Когда окно закрывается,
срабатывает `MainFormClose`, который завершает приложение.

## 5. Слои приложения и их взаимодействие

Проект разделён на слои. Правило проекта: каждый слой делает только свою работу,
а "дальше вниз" передаёт запросы, но не наоборот.

```
   Формы (что видит пользователь)
   ┌──────────────────────────────────────────────────────────┐
   │ uMainForm         — главное окно, вкладки, кнопки         │
   │ uUpdatePupilForm  ─┐                                     │
   │ uUpdatePaymentForm ├─ модальные окна редактирования      │
   │ uUpdateExenseForm ─┘  (наследуют uBaseEditForm)          │
   │ uBaseEditForm        — их общий родитель                 │
   └──────────────────────────────────────────────────────────┘
                    │ вызывает
                    ▼
   Слой данных для гридов
   ┌──────────────────────────────────────────────────────────┐
   │ uMainData — 4 запроса (TFDQuery) + 4 источника (TDataSource)│
   └──────────────────────────────────────────────────────────┘
                    │ берёт данные
                    ▼
   Репозитории — доступ к таблицам (INSERT/UPDATE/DELETE/SELECT)
   ┌──────────────────────────────────────────────────────────┐
   │ uRepositories: TPupilRepository (ученики)                │
   │               TPaymentRepository (поступления)           │
   │               TExpenseRepository (расходы)               │
   └──────────────────────────────────────────────────────────┘
                    ▲   ▲
                    │   └── uServices: TBalanceService.Balance (логика)
                    │
   Инфраструктура — подключение и структура БД
   ┌──────────────────────────────────────────────────────────┐
   │ uDb          — TFDConnection к SQL Server (база foura)   │
   │ uMigrations  — создание таблиц и триггеров               │
   └──────────────────────────────────────────────────────────┘
                    │
                    ▼
            SQL Server (база foura)
```

Ключевой момент: **все** объекты используют **одно и то же соединение
`FDb.Connection`**. Это одна труба к базе, по которой ходят и запросы гридов,
и INSERT'ы репозиториев.

## 6. Детальный разбор каждого модуля

### 6.1. `uDb` — подключение к SQL Server

`TSchoolDb` — тонкая обёртка над `TFDConnection` (ответственный за связь с БД).

Метод `Connect` (`uDb.pas:60`) работает в два этапа:

1. Подключается с параметрами:
   - `DriverID = MSSQL` (драйвер SQL Server),
   - `Server = localhost`,
   - `OSAuthent = Yes` (Windows-вход, без пароля),
   - `Database = foura`.
2. Пока соединение открыто, выполняет:
   ```sql
   IF DB_ID(N'foura') IS NULL CREATE DATABASE [foura]
   ```
   то есть **создаёт базу, если её ещё нет**, а затем переподключается уже
   к созданной базе.

Метод `Migrate` просто делегирует работу классу `TSchoolDbMigrator` из
`uMigrations`.

Свойство `Connection` — то самое общее соединение, которое потом раздаётся
всем репозиториям и `TMainData`.

### 6.2. `uMigrations` — создание структуры БД

`TSchoolDbMigrator.Migrate` (`uMigrations.pas:22`) создаёт таблицы и триггеры.
Создание **идемпотентно**: если запустить повторно, ничего не сломается, потому
что:

- для таблиц проверяется существование:
  ```sql
  IF OBJECT_ID(N'dbo.parents_and_children', N'U') IS NULL CREATE TABLE ...
  ```
- для триггеров используется `CREATE OR ALTER TRIGGER` (пересоздаст, не ошибётся;
  так можно, потому что один `ExecSQL` = один батч, а `IF` + `CREATE TRIGGER`
  в одном батче нельзя).

В программе **данные создаёт не миграция, а только структуру** — таблицы и
триггеры архива. Сами данные приходят либо из дампа `localhost_sqlserver.sql`
(если ставить вручную), либо добавляются самим пользователем через интерфейс.

Триггеры архива автоматически копируют удалённые (или старые) строки в архивные
таблицы `*_arc`.

### 6.3. `uRepositories` — доступ к таблицам (репозитории)

Репозиторий — это класс, который умеет выполнять операции с **одной таблицей**:
положить запись, изменить, удалить, посчитать сумму. Все они получают одно и то
же соединение из конструктора.

| Класс | Таблица | Основные методы |
|---|---|---|
| `TPupilRepository` | `parents_and_children` | `Add`, `Update`, `Delete` |
| `TPaymentRepository` | `money_from_parents` | `Add`, `Update`, `Delete`, `Total` |
| `TExpenseRepository` | `outlay` | `Add`, `Update`, `Delete`, `Total` |

Пример типичного метода (`uRepositories.pas:60`):

```pascal
procedure TPupilRepository.Add(...);
begin
  if Trim(AChildrenName) = '' then
    raise Exception.Create('ФИО ученика обязательно');  // проверка
  FConnection.ExecSQL(
    'INSERT INTO parents_and_children(children_name, parent_name, phone, after_lesson) '
    + 'VALUES (:children_name, :parent_name, :phone, :after_lesson)',
    [AChildrenName, AParentName, APhone, AAfterLesson]
  );
end;
```

Здесь видно два приёма, типичных для этой программы:

1. **Валидация перед записью.** Если данные некорректны (пустое ФИО, сумма ≤ 0,
   не выбран ученик) — выбрасывается исключение `raise Exception.Create(...)`.
2. **Параметризованные запросы.** Вместо склейки строк значения передаются
   через `:имя` параметры и массив значений `[...]`. Это защита от ошибок в
   кавычках и от SQL-инъекций.

Важный нюанс схемы: в таблице поступлений `money_from_parents` нет авто-ID —
`id` совпадает с `id` ученика, поэтому при вставке платежа передаётся `id`
выбранного ученика (`uRepositories.pas:115-119`). А у расходов `outlay` есть
`IDENTITY` — id присваивается базой автоматически.

### 6.4. `uServices` — бизнес-логика

`TBalanceService` — простейший класс, который отвечает за "что значит баланс".

```pascal
function TBalanceService.Balance: Integer;
begin
  Result := FPayments.Total - FExpenses.Total;  // сколько сдали минус сколько потратили
end;
```

Он только сочетает два репозитория. Важно: он **не знает** про базу и форму —
он получает готовые репозитории через конструктор. Это и есть идея разделения:
форма не считает баланс сама, она спрашивает сервис.

### 6.5. `uMainData` — данные для гридов

`TMainData` хранит **4 запроса** (`TFDQuery`) и **4 источника данных**
(`TDataSource`):

| Запрос | Что отдаёт | SQL-запрос |
|---|---|---|
| `PupilsQuery` | список учеников | все поля из `parents_and_children` |
| `PaymentsQuery` | поступления | `money_from_parents` |
| `ExpensesQuery` | расходы | `outlay` **LEFT JOIN** с учениками (чтобы в гриде был и `customer`-id, и имя) |
| `ArchiveQuery` | архив | `UNION ALL` двух архивных таблиц |

Как это связано с гридом:
- `TDataSource` — это "розетка", к которой подключается сетка.
- `TDBGrid.DataSource := FMainData.PupilsSource` (`uMainForm.pas:152`) —
  грид показывает всё, что в данных.
- `RefreshData` (`uMainData.pas:162`) закрывает и заново открывает все 4 запроса
  (т.е. перечитывает таблицы из БД), а потом `ConfigureFields` задаёт русские
  заголовки и ширины колонок.

### 6.6. `uMainForm` — главное окно и "дирижёр"

Это самый большой и важный модуль. Форма содержит (см. `.dfm`):

- `PageControl` с 4 вкладками: **Ученики**, **Сданные деньги**,
  **Потраченные деньги**, **Архив**;
- на каждой вкладке: панель с полями ввода и кнопками (Добавить / Обновить /
  Удалить) + `TDBGrid` с данными;
- внизу `StatusLabel` — строка статуса с балансом.

В приватной части (`uMainForm.pas:91-97`) живут все зависимые объекты:

```pascal
FDb;          // база
FPupils;      // репозиторий учеников
FPayments;    // репозиторий платежей
FExpenses;    // репозиторий расходов
FBalance;     // сервис баланса
FMainData;    // данные гридов
```

Эти поля создаются в конструкторе (раздел 4) и **освобождаются в деструкторе**
`Destroy` (`uMainForm.pas:137`) — в обратном порядке: данные, баланс, репозитории,
база.

**Обновление интерфейса** собрано в одном методе `RefreshData`
(`uMainForm.pas:312`):

```pascal
procedure TMainForm.RefreshData;
begin
  FMainData.RefreshData;       // 1. перечитать все таблицы в гриды
  PopulatePupilCombos;         // 2. пересобрать выпадающие списки учеников
  UpdateStatus;                // 3. обновить строку "Сдано / Потрачено / Баланс"
end;
```

Поэтому после **любой** операции (добавление, удаление, редактирование)
вызывается `RefreshData` — вся форма синхронизируется с базой.

### 6.7. `uUiHelpers` — вспомогательные функции

Небольшие функции, не привязанные к конкретной форме:

- `TodayIso` — сегодняшняя дата в формате `yyyy-mm-dd`.
- `AddPupilComboItem` / `ClearComboObjects` / `GetComboPupilId` /
  `SelectComboPupilId` — работа с выпадающими списками учеников.
- `DisconnectQuery` — безопасное закрытие запроса.
- `SetFieldLayout` — задать заголовок и ширину колонки грида.

**Как спрятан id ученика в комбобоксе.** В обычном `TComboBox` хранится только
текст (ФИО). А нам нужно ещё и число `id`. Поэтому при заполнении списка к
каждой строке прикрепляется объект с id:

```pascal
type TPupilComboItem = class
  public
    Id: Integer;
end;

ACombo.Items.AddObject(DisplayName, TPupilComboItem.Create(APupilId));
```

Потом id читается обратно:

```pascal
Item := ACombo.Items.Objects[ACombo.ItemIndex] as TPupilComboItem;
Result := Item.Id;
```

Все созданные объекты-предки обязаны быть освобождены (`ClearComboObjects`),
иначе утечка. Именно поэтому в `TMainForm.Destroy` перед освобождением поля
вызывается `ClearComboObjects(…)`.

### 6.8. `uBaseEditForm` и наследники — окна редактирования

Это пример **наследования классов** — ключевой идеи ООП.

**База `uBaseEditForm`** (`TBaseEditForm`) — форма с тремя полями
(`Edit1` — Дата, `Edit2` — Назначение, `Edit3` — Сумма) и кнопками ОК/Отмена.
Конструктор принимает три строки и заполняет поля.

В виртуальных методах зашиты значения "по умолчанию":
- `ApplyCaption` → заголовок "Редактирование";
- `ApplyLabels` / `ApplyHints` → подписи полей;
- `Validate` → проверка "дата и назначение не пустые + сумма положительная";
- `ValidateSum` → проверка суммы > 0;
- `GetOperationType` → слово "операция" для сообщений.

Кнопка ОК делает так: если `Validate` вернул `True`, то `ModalResult := mrOk`
(форма закрывается с результатом "ОК"). Если проверка не прошла — показывается
`ShowMessage` и форма не закрывается.

**Наследник платёжной формы `uUpdatePaymentForm` (`TuEditPaymentForm`)**:
он **переопределяет** (`override`) часть поведения родной формы:

```pascal
TuEditPaymentForm = class(TBaseEditForm)

  protected
    procedure ApplyCaption; override;   // заголовок "Редактирование платежа"
```

**Наследник расхода `uUpdateExenseForm`** устроен аналогично — те же 3 поля

## 7. Как проходят реальные сценарии (потоки данных)

### 7.1. Добавление ученика

1. Пользователь вписывает ФИО, родителя, телефон, продлёнку и жмёт
   **«Добавить»**.
2. Срабатывает `AddPupilClick` (`uMainForm.pas:239`).
3. Форма передаёт текст из полей в `FPupils.Add(...)` (`uRepositories.pas:60`).
4. Репозиторий проверяет, что ФИО не пустое, и выполняет `INSERT` через общее
   соединение.
5. Форма очищает поля и вызывает `RefreshData` — в гриде появилась запись.

### 7.2. Добавление платежа (сданные деньги)

1. Пользователь выбирает ученика из `PaymentPupilCombo` и вводит сумму.
2. `AddPaymentClick` (`uMainForm.pas:263`):
   - берёт `id` ученика из комбобокса (`GetComboPupilId`);
   - берёт ФИО по id (`SelectedPupilName` — ищет в `PupilsQuery` через `Locate`);
   - вызывает `FPayments.Add(id, ФИО, сумма)`.
3. Репозиторий проверяет id и сумму и делает `INSERT`, **записывая в
   `money_from_parents` и поле `id` = id ученика** (в этой схеме нет отдельного
   первичного ключа поступлений).
4. `RefreshData` — грид обновился.

### 7.3. Добавление расхода

1. Пользователь выбирает "кто платил", дату (подставлена сегодняшняя от
   `TodayIso`), что купили и сумму.
2. `AddExpenseClick` (`uMainForm.pas:281`) вызывает `FExpenses.Add(id, дата,
   назначение, сумма)`.
3. Репозиторий делает `INSERT INTO outlay ...` — `id` расходу назначает сама
   база (`IDENTITY`).
4. `RefreshData`.

### 7.4. Редактирование по двойному клику (самый интересный сценарий)

Двойной клик по строке в гриде открывает модальное окно. Разберём на примере
расхода (`ExpenseGridDbClick`, `uMainForm.pas:396`):

1. Проверка: если в гриде пусто — выходим.
2. Из текущей строки берутся `id` расхода и `customer` (id ученика-плательщика).
3. Создаётся форма: `TuEditExpenseForm.Create(Self, дата, назначение, сумма)`.
4. `PopulateComboFromPupils(EditForm.PupilCombo)` — наполняет список учеников.
5. `SelectComboPupilId(EditForm.PupilCombo, CustomerId)` — выбирает в списке
   текущего плательщика.
6. `EditForm.ShowModal` — **программа останавливается** и ждёт, пока пользователь
   закроет окно. Возвращается результат (mrOk или mrCancel).
7. Если `mrOk` — `FExpenses.Update(id, id ученика, дата, назначение, сумма)`
   обновляет строку в БД.
8. `finally` — освобождаем объекты комбобокса и саму форму (даже при ошибке).
9. `RefreshData`.

Почему конструкция `try ... finally ... end`? Чтобы форма гарантированно была
уничтожена и память не утекла, независимо от того, что произошло внутри.

### 7.5. Удаление

- `DeletePupilClick` → `FPupils.Delete(id из текущей строки grid)`.
- `DeletePaymentClick` → `FPayments.Delete(id)`.
- `DeleteExpenseClick` → `FExpenses.Delete(id)`.

При удалении платежа или расхода срабатывают **триггеры архива** (раздел 8.1),
которые копируют удалённую строку в архивную таблицу. Поэтому записи в гридах
«Архив» появляются автоматически.

### 7.6. Баланс

`UpdateStatus` (вызывается из `RefreshData`) считает:

```pascal
FPayments.Total - FExpenses.Total
```

где `Total` у каждого репозитория — `SELECT COALESCE(SUM(...), 0) FROM таблица`
(сумма с защитой от NULL). Вывод: "Сдано: X  Потрачено: Y  Баланс: Z".

## 8. База данных

### 8.1. Таблицы

Рабочие таблицы (База `foura`):

| Таблица | Что хранит | Ключевые поля |
|---|---|---|
| `parents_and_children` | ученики | `id` (PK, задаётся вручную), `children_name`, `parent_name`, `phone`, `after_lesson` |
| `money_from_parents` | поступления | `id` = id ученика, `children_name`, `summ_to_first_november` |
| `outlay` | расходы | `id` IDENTITY (база сама нумерует), `date_purchaise`, `item_name`, `customer` (= id ученика), `summ` |

Архивные таблицы (заполняют триггеры):

| Таблица | Когда появляется строка |
|---|---|
| `money_from_parents_arc` | при DELETE или UPDATE платежа (старая версия) + дата `date_ins` |
| `outlay_arc` | при DELETE расхода |

### 8.2. Триггеры

Триггер — это SQL-код, который база выполняет сама при событии. Здесь их три:

- `money_from_parents_delete` — AFTER DELETE: копирует удалённую строку в архив;
- `money_from_parents_update` — AFTER UPDATE: копирует **старую** версию строки
  в архив;
- `delete_from_outlay` — AFTER DELETE: копирует удалённую расходную строку в архив.

Программа про архивы ничего не «знает» — она лишь выполняет DELETE/UPDATE,
а база сама ведёт историю. Поэтому вкладка «Архив» показывает строки, которых
уже нет в рабочих таблицах.

### 8.3. Почему в программе так много JOIN и совпадений id

В этой (дамп-схеме) связи между учеником и его платежом/расходом выражены через
совпадение `id`: у поступления `id` равен `id` ученика, у расхода поле
`customer` содержит `id` ученика. Поэтому:

- для имени плательщика в гриде расходов используется `LEFT JOIN`
  (`uMainData.pas:81-85`);
- выпадающий список учеников строится из `PupilsQuery`, а внутрь списка
  «приклеивается» `id` (раздел 6.7).

## 9. Схема взаимодействия «кто кого вызывает» (граф)

```
SchoolExpensesDemo.dpr
        │
        ▼
TMainForm.Create ──────────────┬──▶ TSchoolDb.Create/Connect/Migrate
                               │          │
                               │          ▼
                               │   TSchoolDbMigrator.Migrate (таблицы+триггеры)
                               │
                               ├──▶ TPupilRepository.Create(Connection)
                               ├──▶ TPaymentRepository.Create(Connection)
                               ├──▶ TExpenseRepository.Create(Connection)
                               ├──▶ TBalanceService.Create(FPayments, FExpenses)
                               ├──▶ TMainData.Create(Connection)
                               │         │  CreateQuery → 4 × TFDQuery
                               │         │  + 4 × TDataSource
                               ├──▶ BindDataSources (гриды ↔ DataSource)
                               └──▶ RefreshData
                                         ├─ TMainData.RefreshData (Open запросов)
                                         ├─ PopulatePupilCombos (комбобоксы)
                                         └─ UpdateStatus (FBalance.Balance)

События кнопок (после запуска):
  AddPupilClick    → TPupilRepository.Add      → ExecSQL(INSERT)
  DeletePupilClick → TPupilRepository.Delete   → ExecSQL(DELETE)
  AddPaymentClick  → TPaymentRepository.Add    → ExecSQL(INSERT)
  ...
  ГридDblClick     → TuEdit*Form.ShowModal → репозиторий.Update → ExecSQL(UPDATE)
  RefreshClick     → RefreshData
```

Ключевая мысль: **форма сама не пишет SQL**. Форма знает только объекты (кнопки,
гриды, комбобоксы) и вызывает методы репозиториев. Репозитории знают только SQL.
Сервис знает только репозитории. Благодаря этому можно, например, поменять
названия таблиц в одном модуле, не трогая форму.

## 10. Словарик терминов для новичка

| Термин | Значение |
|---|---|
| VCL | Библиотека визуальных компонентов Delphi для Windows (формы, кнопки, гриды). |
| DFM | Файл описания формы: где лежат компоненты. |
| TForm | Базовый класс окна. Наши формы наследуют его. |
| FireDAC | Мощная библиотека доступа к БД от Delphi. |
| TFDConnection | Объект соединения с БД (одна труба к SQL Server). |
| TFDQuery | Объект запроса: в нём лежит SQL-текст и результат (таблица). |
| TDataSource | «Розетка» между набором данных и визуальным компонентом (гридом). |
| TDBGrid | Таблица-грид на форме, показывает данные из TDataSource. |
| TComboBox | Выпадающий список. |
| ShowModal | Открыть форму модально (заблокировать остальное окно) и ждать результата. |
| mrOk / mrCancel | Коды результата модального диалога (ОК=1 / Отмена=2). |
| ExecSQL | Выполнить запрос, не возвращающий набор строк (INSERT/UPDATE/DELETE/CREATE). |
| ExecSQLScalar | Выполнить запрос и вернуть одно первое значение (например, SUM). |
| Параметризованный запрос | Запрос с `:name`-параметрами — значения подставляются безопасно. |
| Агрегат SUM / COALESCE | `SUM` — сумма; `COALESCE(x, 0)` — если x пусто (NULL), вернуть 0. |
| Триггер | SQL-код в базе, который срабатывает сам при INSERT/UPDATE/DELETE. |
| IDENTITY | Поле, которое база нумерует автоматически (1, 2, 3, ...). |
| Репозиторий | Класс, инкапсулирующий запросы к одной таблице. |
| Инъекция | Подстановка вредоносного кода в SQL. От неё защищают параметры. |

## 11. Частые ошибки новичка и куда смотреть

| Симптом | Почему | Где смотреть |
|---|---|---|
| `E2003 Undeclared identifier: ...` | Забыли модуль в `uses` | все `.pas`, начало каждого файла |
| Кириллица превратилась в «?????» | Файл без BOM / не та кодировка | все `.pas`, `.dfm` (см. `agents.md`) |
| «Неправильный синтаксис около TRIGGER» | `CREATE TRIGGER` в одном батче с `IF` | `uMigrations.pas` — надо `CREATE OR ALTER TRIGGER` |
| Грид пустой при запуске | Нет базы/таблиц, или не вызван `RefreshData` | `uMainForm.Create`, `FDb.Connect/Migrate` |
| Кнопка не реагирует | Нет `OnClick` в `.dfm` | `uMainForm.dfm`, `uBaseEditForm.dfm` |
| Ошибка «Выберите ученика» | В комбобоксе нет выбранного id | `GetComboPupilId`, `PopulatePupilCombos` |
| Утечка памяти при `Create` | Забыли `Free` / `ClearComboObjects` | `TMainForm.Destroy`, `uUiHelpers` |
| Сумма не считается | NULL в сумме | `COALESCE(SUM(...), 0)` в `Total` |
